## Q1. Draft-model-free speculation: evidence on code / agentic / editing workloads

### 1.1 Empirical study of SD on software-engineering tasks (ISSTA 2026, the most relevant controlled data)
Li, Chen, Hu, Xia, "An Empirical Study of Speculative Decoding on Software Engineering Tasks", Proc. ACM Softw. Eng. 3 (ISSTA), arXiv 2604.26469v4. vLLM on A800 80GB. PLD: lookup window N=4, draft K=5; Suffix Decoding K=32; EAGLE-3 official RedHatAI drafters. Table 1 (speedup x / mean acceptance length tau):

Qwen3-30B-A3B (MoE, the closest architecture to Inkling 2 Mini):
- PLD: LiveCodeBench 0.87x/2.21, HumanEval 0.99x/2.57, SWE-bench 1.02x/3.25, Defects4J 1.36x/3.38, Aider Polyglot 1.08x/3.29, CanItEdit 1.55x/3.83 (mean 1.15x/3.09)
- Suffix Decoding: LiveCodeBench 0.95x/1.02, HumanEval 1.03x/0.91, SWE-bench 1.73x/4.78, Defects4J 1.53x/3.14, Aider 0.99x/1.41, CanItEdit 1.83x/2.93 (mean 1.34x/2.37)
- EAGLE-3: 0.77x, 0.54x, 0.41x/0.43, 0.55x, 1.15x, 0.87x (mean 0.72x/1.57)
Llama-3.1-8B: Suffix Decoding SWE-bench 3.35x/5.48, CanItEdit 2.90x/3.54; PLD CanItEdit 2.05x/4.01.
Findings quoted: "Across SWE-bench and Defects4J, Suffix Decoding achieves an average speedup of 2.14x, compared with 1.44x for PLD and 0.90x for Eagle-3. Across Aider Polyglot and CanItEdit, Suffix Decoding reaches 1.91x, compared with 1.52x for PLD and 1.38x for Eagle-3." "Suffix Decoding achieves a mean tau of 1.09 on code generation benchmarks, compared with 3.79 on code repair benchmarks and 2.75 on code editing benchmarks." "model-based approaches are well-suited for code generation, whereas model-free methods are better adapted to repository-level repair and editing scenarios." "SE tasks can accommodate more aggressive hyperparameters (i.e., a larger number of draft tokens)" (K=5 beat K=3).
Repetitiveness (Table 4, share of output n-grams that recur in context): code 2-gram 28.64%, 3-gram 17.66%, 4-gram 12.68%, 5-gram 9.62%; natural language 28.66 / 15.40 / 9.63 / 6.85%. Also: PLD's O(context) scan is called out as a cost ("PLD's N-gram retrieval entails a complexity of O(T)"), so use an indexed structure at 7k+ contexts.
URL: https://arxiv.org/pdf/2604.26469

### 1.2 AgSpec (retrieval SD in coding-agent pipelines, arXiv 2610.01108, Oct 2026)
vLLM, SWE-bench Verified + TeamBench, Devstral-24B / Gemma3-27B / Qwen3.6-27B. Key quotes:
- "AgSpec ... reaching 2.27-4.37x the throughput of autoregressive decoding at batch size 1"; on multi-turn LiveCodeBench "4.87-7.94x".
- Corpus matters more than the matcher: "replacing a per-call corpus with the session corpus raises AL by 1.6-2.1x, as agents repeatedly reproduce code and outputs from earlier calls. The workspace corpus adds 26-47% on its own". Index files "in the forms the agent emits" (e.g. diff-prefixed lines): "raising the coder's AL by 13-39%" in the first turn.
- Draft length: "K_i = clip(round(alpha(a_i) m_i), 1, Kmax)" with m_i = match length; cap "Kmax = max{k : Pr(R >= k) >= lambda}" where lambda is "the acceptance probability at which one more draft position covers its verification cost" (their GPU example lambda=0.1; for inkcpu lambda ~0.3, see Q2). Online scale alpha updated by a quantile step "alpha <- alpha + eta(tau - I[A_i < D_i])". Effect: "The online scale alone raises throughput by 66%, as the share of rejected draft tokens falls from 78% to 50%"; "without it, the drafter spends about 26 tokens per step over the first 160 steps but has fewer than 2 accepted; with it, the drafter shortens its drafts to about 4 tokens".
- Realised accept lengths on SWE-bench (Devstral, bs1): fixed K=32 AL 6.0, AgSpec 5.5, drafts grow "from about 10 tokens in early turns to 21 in the fifth"; K=32 "rejects 11-26 tokens per step, whereas AgSpec rejects at most 6".
- "AgSpec drafts on 98-99% of request steps, compared with 50-56% for SAM-Decoding" (availability, not matcher quality, is the limiter).
URL: https://arxiv.org/pdf/2610.01108

### 1.3 SuffixDecoding (Oliaro et al., NeurIPS; Snowflake ArcticInference)
- Paper v1 Table 2 (Llama-3-70B, 8xH100): accepted tokens/step AgenticSQL 1.57-5.08 (acceptance rate 0.14-0.41 of 11-32.4 speculated tokens), Spider 1.7, WildChat 1.79, Magicoder (code gen) 2.11; speedups AgenticSQL up to 2.9x throughput, Magicoder/WildChat up to 1.4x. Spec length rule "MAX_SPEC(p) = alpha*p, alpha in [1,4]" (p = matched pattern length). https://arxiv.org/html/2411.04975v1
- Later version abstract: "speedups of up to 5.3x ... 2.8x faster than model-based approaches like EAGLE-2/3 and 1.9x faster than model-free approaches such as Token Recycling" on SWE-Bench/Text-to-SQL. https://arxiv.org/pdf/2411.04975
- Snowflake blog: "1.8x-4.5x speedups on end-to-end SWE-Bench task completion", "20 microseconds per speculated token on the CPU", and it "can be combined with draft-model speculation". https://www.snowflake.com/en/engineering-blog/fast-speculative-decoding-vllm-arctic/ (production post https://www.snowflake.com/en/blog/engineering/suffixdecoding-arctic-inference-vllm/ returned 403; search snippet: "outperforms N-gram speculation in vLLM at all concurrency levels").
- Third-party caveat (FailFast, arXiv 2512.20573): pattern matcher, "few matches" on HumanEval/math.
- In the SE study above, Suffix Decoding on Spec-Bench-style categories gives Token Recycling 2.3-3.1 accepted tokens; in agentic settings "6.3 mean accepted tokens per step vs EAGLE-3 3.6 and Token Recycling 3.2" (search snippet of arXiv 2411.04975).

### 1.4 SAM-Decoding, PLD, PLD+, Token Recycling, lookahead
- SAM-Decoding (ACL 2025, arXiv 2411.10666): Spec-Bench PLD 1.75 accepted tokens / 1.56x; SAM 2.30 / 1.84x; SAM+Token Recycling 2.27x; SAM+EAGLE-2 2.49x; HumanEval Token Recycling 1.99x -> SAM+TR 2.16x. Adaptive selection "dynamically choose between automaton-generated drafts or auxiliary speculative decoding methods based on matching length" = the hybrid we want. https://arxiv.org/abs/2411.10666
- Token Recycling: top-K adjacency from target logits, "static 80-node tree" (RECAP, arXiv 2611.05894); Spec-Bench 2.3-3.1 accepted tokens on GPU trees. Chain-only on CPU would give well under DSpark's 2.5-3.3; not worth it while DSpark exists.
- PLD+ (arXiv 2412.01447): uses hidden states / induction heads (best K=70, layer 9; 50 induction heads); includes code-editing tasks but no table extracted. Requires attention-score access per step; moderate complexity, no clear win over suffix matching.
- NgramRL (arXiv 2610.32881): per-prompt keying 3.05 accepted tokens/step vs 2.41 global; acceptance saturates beyond n-gram order 6.
- OWL (arXiv 2510.07535): PLD 1.41 (SpecBench) vs 2.75 (LongSpecBench) accepted tokens; retrieval methods gain with longer context, which favours 7k-token prompts.
- Lookahead/Jacobi (LMSYS, arXiv 2402.02057): ">2x" on HumanEval with CodeLlama but "7B, 13B, and 33B models require 120x, 80x, and 56x extra FLOPs per step"; explicitly weaker on FLOP-limited hardware. Not viable on an ALU-bound CPU verify.

### 1.5 Draftless modes in llama.cpp and Inkling-specific community numbers
- docs/speculative.md: `--spec-type ngram-simple|ngram-map-k|ngram-map-k4v|ngram-mod|ngram-cache` (comma-separable with a draft model; "If a draft model is combined with a draftless decoding the draftless decoding has higher precedence"). ngram-simple: match the last n-gram (default n=12) and draft the following m tokens (default m=48); ngram-map-k adds `min-hits`. https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md
- RTX 3090 study, Qwen3.6-35B-A3B (same 128-expert/top-8 class), chat prompts: ngram-map-k4v "drafted 216 tokens across 27 000 generated, one per 125, so its acceptance rate is 108 of 216 and it neither helps nor hurts"; probabilistic modes hurt: ngram-mod -10.9%, ngram-cache -19.0% (5% acceptance); dflash n2 +26.3% at 72.3% acceptance. Lesson: fire only on long exact matches; never use statistical n-gram caches on this hardware. https://github.com/thc1006/qwen3.6-speculative-decoding-rtx3090
- RustingStrata PR #74 (Inkling 2 Mini UD-Q3_K_XL, 4 GB GPU, pp512/tg64 microbenchmark): suffix drafts "112/112 drafts accepted", 8.6 -> 16.3 tok/s; "Adding the DSpark --draft-model on top is not worth it: its drafts drop acceptance to 89% and decode fell to 15.7 tok/s". https://github.com/RustingStudio/RustingStrata/pull/74
- HN (ROCm, Q4): "63 tok/s decode (70-110 code, n-gram)". https://news.ycombinator.com/item?id=50581260
- AdaSpark (arXiv 2610.05774, llama.cpp-style engine, DSpark drafters): n-gram continuations of the request's own text compete with drafter candidates for verify rows under one acceptance model; on the MoE target (LFM2.5-8B-A1B) verify time "rises with every row, because each row is routed to its own experts"; T(16)/T(2) = 2.16 for the MoE vs 1.11-1.57 for dense targets; pinned widths 4-16 rows were "5-14% slower" than the learned width. Confirms that on MoE targets narrow, well-priced drafts win. https://arxiv.org/pdf/2610.05774

## Q2. Break-even and expected speedups under the inkcpu cost model

Model: step time = d + V(T) plain steps (d = 0 for lookup, 0.30 for DSpark); tokens emitted = accepted + 1; i.i.d. per-token acceptance p gives E[acc] = sum_{k=1..T} p^k. V(T) for T>8 extrapolated at 0.32 plain/row (must be re-measured).

Break-even accepted tokens per verify (free drafter): T=2: 0.45, T=3: 0.90, T=4: 1.15, T=5: 1.65, T=6: 1.97, T=7: 2.30, T=8: 2.43 (per-token acceptance >= 0.22-0.33). With DSpark (d=0.30): T=2: 0.75, T=3: 1.20, T=4: 1.45, T=6: 2.27, T=8: 2.73 (per-token >= 0.34-0.40).
Marginal verify row cost 0.25-0.50 plain -> lambda (AgSpec cap) ~0.3 for this engine, vs 0.1 on their GPUs. Tree siblings need >= 30-45% conditional acceptance each to pay.

Speedup vs plain, free drafter, by per-token acceptance p (T=2/3/4/5/6/7/8):
 p=0.50: 1.21/0.99/0.90/0.74/0.67/0.60/0.58 ; p=0.70: 1.51/1.33/1.29/1.11/1.03/0.95/0.93
 p=0.80: 1.68/1.55/1.56/1.39/1.33/1.26/1.26 ; p=0.90: 1.87/1.81/1.90/1.77/1.76/1.73/1.79
 p=0.95: 1.97/1.95/2.10/2.00/2.03/2.04/2.16 ; p=0.98: 2.03/2.04/2.23/2.15/2.22/2.26/2.42
Pure copy mode with extrapolated long drafts: p=0.98: T=8 2.42x, T=12 2.45x, T=16 2.43x, T=24 2.32x; p=0.95: T=8 2.16x, T=16 1.94x; p=0.90: T=8 1.79x, T=16 1.39x. => cap lookup drafts at 8-12 rows unless the match is very long and acceptance history is >=0.97.
DSpark-only by T (p implied from measured acc at T=4): code (acc 3.3, p~0.92): T=2 1.59x, T=4 1.76x, T=8 1.80x; pooled (2.5, p~0.82): T=2 1.43x, T=4 1.43x, T=8 1.24x; prose (1.65, p~0.68): T=2 1.22x, T=4 1.08x, T=6 0.88x.

Workload estimates (steps split into copy-mode where a match >= n exists, with conditional acceptance p_c, and generate-mode handled by DSpark T=4 at measured acceptance):
 (a) code edit, 50% of steps copyable (p_c 0.95, T 8): hybrid 1.99x; lookup+plain 1.90x; DSpark-only 1.76x. 70% copyable: ~2.0x.
 (b) code gen, 15-25% copyable (p_c 0.85): hybrid 1.67-1.70x vs DSpark-only 1.76x (neutral; the DSpark path dominates).
 (c) prose, 5-10% copyable: hybrid 1.10-1.18x vs DSpark-only 1.08x; with adaptive T=2 DSpark ~1.22x.
Assumptions: i.i.d. acceptance (real copy runs are burstier, which favours longer drafts when the match is long and short ones otherwise, i.e. match-derived length); copy-mode share taken from the SE study's tau gap (edit 2.75-3.79 vs gen 1.09 for suffix decoding) and AgSpec's 1.6-2.1x AL gain from session corpora; no change to verify(T) from mixing drafters; prefill unchanged.

## Q3. Model drafters: DSpark data, EAGLE-3/HASS/Medusa, tree verification on CPU

- DSpark (Unsloth README, HF unsloth/Inkling-2-Mini-GGUF/dspark/README.md): "general.architecture = dflash", 54 tensors, "taps those looped layers", "borrows the target's embeddings and output head"; Q8_0 "accepts drafts at the same rate as BF16"; default `--spec-draft-n-max 3`; no acceptance figure published. Unsloth run-locally guide: "--spec-draft-n-max 2 is the fastest depth for Inkling 2 on this build (the third draft token is rarely accepted)". https://huggingface.co/unsloth/Inkling-2-Mini-GGUF/blob/main/dspark/README.md , https://unsloth.ai/docs/models/inkling-2-mini
- Community acceptance for the official MTP/DSpark head: MTPLX greedy depth 3 "2.29 tokens per verify round (441/1066 drafts accepted, 41.4%)", 3-bit "2.48 tokens/round ... ~1.51x" (https://huggingface.co/barozp/Inkling-2-Mini-MTPLX-3bit); vLLM DGX Spark temp 1.0, 7 tokens: "draft acceptance rate was about 19%", "47.7 tok/s with MTP on vs 55.5 with it off" (https://dev.classmethod.jp/en/articles/dgx-spark-inkling-2-mini-first-touch/); llama.cpp 16 GB GPU: 56.4 -> 77.7 tok/s with n-max 2 (https://huggingface.co/drofn/Inkling-2-Mini-16GB-GGUF); HN favourable prompt "draft acceptance = 0.83204 (535/643), mean len = 6.00"; ninfer-all essay prompt 133/832 drafts (16%) at 7 drafts, llama.cpp 37.0 tok/s with DSpark vs 57.3 without, but adaptive drafting 115.6 vs 103.1 (https://github.com/iamwavecut/ninfer-all/blob/master/docs/inkling2.md); ninfer-3090 PR #539 per-position acceptance "p0 15.7% (llama.cpp 10.1%), p1 48.6%" on unfavourable prompts (https://github.com/ashalliants/ninfer-3090/pull/539). Our measured 2.4-2.6 (pooled) / 3.1-3.5 (code) at T=4 is at the top of the reported range.
- EAGLE-3 / HASS / Medusa for Inkling 2 Mini: none found (search over HF/GitHub returned only the official MTP head and quant repos). EAGLE-3 in llama.cpp (PR #18039) claims 2-3x on CUDA but "after disabling CUDA graphs for llama-cli ... roughly a 1.5x speedup"; no CPU numbers. The SE study shows EAGLE-3 drafter quality is training-data dependent (tau 2.00 vs 0.57 between two drafters for the same L31-70B target) and 0.72x on the MoE Qwen3-30B-A3B.
- Tree verification on CPU: Sequoia (arXiv 2402.12374) states "for large trees the verification time can no longer be approximated as a constant ... Hence there exists an optimal tree size", and chooses 64-128-node trees on-device vs 768 when offloading (memory-bound). Our verify is ~linear in rows (0.25-0.50 plain/row), so the optimum is a chain of 2-8; AdaSpark's MoE result (pinned widths 4-16 rows 5-14% slower than learned width; MoE T(16)/T(2)=2.16) agrees. Conclusion: no tree; chain with adaptive length.

## Q4. MoE-specific speculation

- Expert union growth: "Speculative Decoding for MoE Models: Expert Bytes, Kernel Bandwidth and the Best Draft Length" (arXiv 2610.34440): distinct experts for n tokens under uniform routing "N(1-q^n) with q = 1-m/N"; for 128/8 that is 8 (n=1), 29 (n=4), 52 (n=8). "Next-token expert reuse has been measured at 44 to 48% on Qwen3-30B-A3B". Leviathan condition "some draft length is faster than plain decoding exactly when a > chi" (chi = per-draft-token cost relative to a step); best draft length is "a monotone staircase in the acceptance rate". Deduplicating expert kernels were faster than per-slot kernels "only from 5 to 8 tokens per pass, or never" on GPU/Metal; on our ALU-bound CPU the relevant question is whether verify time tracks rows (ALU) or union bytes (memory): measure it (rec #8).
- SP-MoE (arXiv 2510.10302): "Neighboring draft tokens exhibit overlapping expert activations"; Prefetch-Steered Routing (arXiv 2610.34721): OLMoE verification at k=16 needs "about 40 of OLMoE's 64 experts per layer" so SD "copies more expert bytes per committed token than AR" under offloading. DraftExpert (arXiv 2607.24434): dense SD "benefits from the fact that verifying multiple tokens reuses the same dense FFN weights - which MoE breaks".
- S2-MoE (arXiv 2608.15018, llama.cpp with expert offloading on Jetson Orin / RTX 4090): draft = same model with fewer experts (e.g. 1 vs 6); admission rule "U_i = p_i*T_AR / (dC_ver(i|S) + C_i^draft)", admit while U_i >= 1; reuse-aware gating is LOSSY ("PPL ratio ... 1.012-1.013", "Top-1 agreement ... >89%", KL 0.026-0.065) so it is excluded for a lossless engine; speedups "1.3x-5.3x on Jetson Orin and 1.2x-2.9x on RTX 4090" come from I/O-bound offloading, not our regime. The utility rule itself is adoptable (price each extra draft row by the experts it newly activates) if Q4 measurement shows union bytes matter.
- No CPU-only MoE speculation numbers were found.

## Q5. Self-speculation for a looped model

- Inkling 2 Mini architecture (Thinking Machines): "24 layers, divided into four blocks of six layers each. The two middle blocks run three times, while the first and last blocks each run once"; "Every pass starts with the output of the prelude (the first block). The second and third passes through the middle blocks also read the middle blocks' outputs from the previous pass, which we call the message." Fixed at 3 passes. https://thinkingmachines.ai/news/inkling-2-mini/
- Fewer passes (TML-d24-varloop-research, trained 1-5 passes "sampled in a 1:2:6:2:1 ratio", post-trained at 3): DeepSWE v1.1 1/2/3/4/5 passes = 0.7% / 28.3% / 47.4% / 46.9% / 48.2%; SWE-bench Verified 56.3 / 76.5 / 78.7 / 79.3 / 79.6%; SWE-bench Pro v2 39.7 / 69.1 / 78.9 / 76.0 / 78.4%. "Because 3 passes dominated training ... performance at other pass counts may understate". https://huggingface.co/thinkingmachines/TML-d24-varloop-research . Inkling 2 Mini itself was never trained at 1-2 passes, so a shallow readout is out of distribution; token-level agreement is unmeasured anywhere.
- Cost: a sequential 1-pass draft runs 24 of 48 layer visits (~0.5 plain step per draft token; 2-pass ~0.75) vs DSpark's 0.30 per 3-7-token block, so sequential self-drafting cannot beat DSpark. Pipelined schemes reuse shallow states: LoopSpec (arXiv 2609.17184, training-free, RTX PRO 6000): Raven-Llama-3.2 R=32 "depth-1 greedy agreement exceeds 86% and surpasses 99% by depth 8" on GSM8K, "up to 6.83x"; Dory1.0-4B (arXiv 2611.03998): draft at k=1, verify at k=4, "1.37-1.71x"; CopyLoop (arXiv 2610.38822, RTX 5090, BF16) = context-copy drafts + shallow screening, Table 1 HumanEval+: Ouro-1.4B PLD 2.73x / LoopSpec 3.24x / CopyLoop 6.04x; Huginn-3.5B PLD 2.05x / LoopSpec 3.73x / CopyLoop 4.67x; "yields greater speedups on longer generations with reusable contexts". Depth-adaptive paper (arXiv 2608.09444): "fully looped architectures are best suited ... large non-looped layers outside the recurrent core ... slow down and complicate scheduling" - Inkling has 12 unshared layers (25% of visits) and only 3 passes, so headroom is far below Ouro/Raven (R=4-32). Huginn (arXiv 2502.05171) notes recurrent KV entries from different depths "match" because the same K,V projections are used, which also holds for Inkling's shared middle blocks.
- Verdict: research-grade; do a 1-day agreement measurement before anything else.

## Implementation sketch for recommendation #1 (session-lookup drafter)
1. Index: suffix automaton (or hash map of 8-12-token keys) over prompt tokens, every token generated so far, and tool results as they arrive; rebuild incrementally per token (SuffixDecoding: ~20 us/token on CPU). For file edits, also index opened files in the emission form Caret uses (diff-prefixed lines) per AgSpec (+13-39% AL on first turn).
2. Fire only when the longest suffix match m >= n_min (start n_min = 8-12 like llama.cpp's code default of 12; AgSpec/SuffixDecoding use longest-match). Draft length K = clip(round(alpha*m), 1, Kcap) with Kcap = 8 now (12-16 after re-measuring verify slope), alpha adapted online by the AgSpec quantile step with tau = 1 - lambda, lambda ~ 0.3 (our marginal row cost).
3. Precedence: lookup draft when it fires, else DSpark chain with adaptive T (rec #2). Later (rec #3): when both fire, verify DSpark block rows plus the lookup chain in one batch, ordered by estimated acceptance.
4. Telemetry: per-mode fire rate, accepted/offered per position, realised speedup; the RTX 3090 study shows fire rate (1 in 125 steps on chat) is the number that decides whether the mode matters.
