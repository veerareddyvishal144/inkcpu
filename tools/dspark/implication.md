**Recommendation.**
1. **Build it, as an adaptive mode and only with the lm_head fold; do not build always-on speculation.** A fixed T = 4 averages a modest gain ({{SPM_greedy_3}}x M, {{SPQ_greedy_3}}x Q pooled) because it wins 1.3-1.8x on structured text and reasoning and loses 13-18% on plain conversation; fixed T = 8 ({{SPM_greedy_7}}x pooled) only pays on code and tool calls (about 2x) and loses up to 40% on conversation. The per-prompt best choice reaches {{MACRO_ORACLE_M}}x (M).
2. **Policy**: verify width T in {1 (plain), 4, 8}. Keep a running estimate of cumulative acceptance per draft position (EWMA of acc@j over the last ~16 steps), pick the T that maximises L(T)/S(T) with S from the bytes table (section 8), fall back to plain decoding while L(4) < about 2.0 (L*(4) = {{BEM_3}} M / {{BEQ_3}} Q), re-probe every ~32 tokens. T = 2 (needs L > 1.57, c@1 about 0.6 gives about 1.6), T = 5, 6, 7 add nothing over {4, 8}. The model has no confidence head (section 7), so this is engine policy.
3. **Prerequisites**: the fold M = lm_head x hidden_out (+102 MB resident, 102 MB read per chained position; Q8_0 54 MB) and a bf16 or Q8_0 drafter (Unsloth reports the same acceptance for Q8_0); tap capture of 3 visit inputs + the final state for all T rows; rejection sampler for T > 0; target conv-state restore to row k.
4. **Do not use this llama.cpp build as the speed baseline.** It runs the target lm_head twice per chained position (variant C: {{SPC_greedy_3}}x at n = 3 and {{SPC_greedy_7}}x at n = 7 in the bytes model) and its T = 4 verify step takes about {{TT_greedy_3}} ms against roughly 190-200 ms for one token (drafting alone {{TD_greedy_3}} ms per step); section 9.3 has the measured tokens/s. The gains above exist only for an engine that implements the fold and keeps the verify step near the ROUTING.md bytes (1.7x one token at T = 4).
5. **Risks that could change the verdict**: (a) the T = 4 / 8 verify must stay bandwidth-bound on AVX-512 without VNNI (ROUTING caveat 2); (b) ROUTING.md measured expert overlap on true continuations, rejected drafts are off-distribution and under independent routing S(4) grows by about 2.2 GB (3.64x instead of 2.47x the one-token expert bytes), which would turn the pooled T = 4 estimate into a loss of about 9%; (c) real agentic traffic is more structured than this mix (Inkling Small deployments report 3.3-3.5 tokens per step at 7 drafts and temperature 1.0 on 32K-256K agentic sessions, vLLM blog; RadixArk's Small drafter 3.7-3.8 on benchmarks), which favours T = 8; (d) this used a Q4_K_XL target and a Q8_0 lm_head, not the bf16 target the drafter was trained on; (e) 8 prompts x 80 tokens is a small sample.
